# Laravel, PHP and MySQL

## How does a request flow through a Laravel application?

The request enters through `public/index.php`, which boots the framework and the
service container. It then passes through global middleware, is matched against
the routes, passes through the route's middleware (authentication, throttling,
role checks), and reaches a controller method. The controller returns a
response — a view, JSON or a redirect — which travels back out through the same
middleware.

Knowing this order explains where things belong: cross-cutting checks in
middleware, request validation in Form Requests, business logic in service
classes or actions rather than fat controllers, and data access in Eloquent
models.

## What is Eloquent, and how do you avoid the N+1 problem with it?

Eloquent is Laravel's ORM. Each table has a model class, and relationships such
as `hasMany` and `belongsTo` are methods on the model, so `$order->items`
returns the order's items.

That convenience hides a trap: looping over orders and reading `$order->customer`
runs one query per order. Eager loading with `Order::with('customer', 'items')->get()`
loads the related rows in a couple of queries instead. Laravel can be told to
throw an error on lazy loading during development
(`Model::preventLazyLoading()`), which catches N+1 problems before they reach
production.

## How do Laravel migrations and seeders work?

Migrations are PHP classes with `up` and `down` methods that create or change
tables through the schema builder. They are versioned in the repository and run
in order with `php artisan migrate`, so every environment ends up with the same
schema. `migrate:rollback` runs the `down` methods.

Seeders insert data — reference data such as roles and permissions, or fake
records generated by factories for development and tests. A deployment should
only run migrations; seeding production with fake data is a mistake, while
seeding required reference data should be idempotent.

## How do you validate input in Laravel?

The cleanest way is a Form Request class: its `rules()` method declares the
validation rules and `authorize()` decides whether the user may make the request
at all. When validation fails, Laravel redirects back with errors for web forms
or returns a 422 JSON response for API requests, before the controller runs.

After validation, use `$request->validated()` rather than `$request->all()` so
only the fields you declared reach the model. Combined with `$fillable` on the
model, this prevents mass assignment, where an attacker adds a field such as
`is_admin` to a request and it gets saved.

## How is role-based access control done in Laravel?

Authentication answers who the user is; authorization answers what they may do.
Laravel provides Gates for simple checks and Policies for rules about a
particular model, such as "a user can update an invoice only if they created it
or are a manager".

Routes can be protected with middleware (`can:update,invoice`), controllers call
`$this->authorize()`, and Blade templates use `@can` to hide buttons. Hiding a
button is only for user experience; the real enforcement must happen on the
server, because any request can be sent directly. Roles and their permissions
are usually stored in tables so they can change without a deployment.

## What does the service container do?

The service container is Laravel's dependency injection system. When a
controller's constructor asks for a `PaymentGateway` interface, the container
creates the configured implementation and passes it in. Bindings are registered
in service providers.

This keeps classes depending on interfaces rather than concrete classes, so a
real payment gateway can be swapped for a fake one in tests, or for another
provider, without changing the code that uses it.

## How do queues work in Laravel?

Slow work — sending email, generating a PDF report, calling an external API — is
put into a job class and dispatched to a queue backed by Redis or the database.
A separate `php artisan queue:work` process picks jobs up, so the user's request
returns immediately.

Jobs can be retried with a backoff, and jobs that keep failing are moved to the
failed jobs table where they can be inspected and retried. Because a job can run
more than once, it should be idempotent: sending the same invoice email twice,
or charging twice, must be prevented by checking whether the work was already done.

## What are the practical differences between MySQL and PostgreSQL?

Both are reliable relational databases with transactions and MVCC. Differences
an application developer notices: PostgreSQL has transactional schema changes,
so a failed migration rolls back completely, while most MySQL schema changes
commit immediately and can leave a migration half-applied. PostgreSQL has richer
types — JSONB with indexing, arrays, native UUIDs — and extensions such as pgvector.

MySQL's default collations compare strings case-insensitively, which surprises
people coming from PostgreSQL, and InnoDB organises tables around the primary
key, which makes random UUID primary keys slower to insert. For typical web
applications either is fine; the choice is usually made by the hosting, the
framework's habits or the team's experience.
